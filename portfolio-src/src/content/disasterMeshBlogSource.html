I built an Android app that works when everything else goes down — here’s what real-world mesh networking actually looks like

DisasterMesh is a decentralized Android communication system that lets nearby devices discover each other, exchange messages, and relay information across multiple hops — all without internet, cellular towers, or a central server. This is the full build walkthrough.

Most communication systems are built on a single assumption: the internet will always be there. In real-world disaster scenarios — earthquakes, floods, large-scale outages — that assumption fails immediately. Cellular towers go down. Wi-Fi infrastructure disappears. The people who need to communicate most are the ones suddenly cut off.

That is where this project started. The question was simple: what if devices could communicate without internet, without cellular towers, and still form a usable network? The answer turned into DisasterMesh — a peer-to-peer Android application that uses Bluetooth and Wi-Fi Direct to build a dynamic mesh where each device acts as both a node and a relay.

The real problem: propagating information across disconnected nodes

This is not just a chat app without Wi-Fi. The genuinely hard problem is different. If device A is not directly connected to device C, but both connect to B — can A still send a message to C? That is the core challenge: discovery, routing, and reliability across a network that has no fixed topology and no central coordinator.

How the mesh actually works

At a high level, DisasterMesh behaves like a dynamic mesh network. Every device acts as both a client and a relay. When a message is sent, it does not travel down a fixed route — it propagates outward through whatever connections are available at that moment.

Device discovery: easy in theory, hard in practice

DisasterMesh uses the Google Nearby Connections API, which handles Bluetooth and Wi-Fi Direct transport without requiring internet. Devices advertise themselves, nearby devices discover them, a connection is established, and data exchange begins.

The API handles the transport layer well. What it does not handle is the instability of real-world conditions. Devices move, disconnect, and reappear constantly. The system has to treat connection loss as a normal operating state, not an error condition.

Discovery is the easy part. Maintaining stable connections in a mobile environment where devices are constantly moving is where the real engineering problem lives. The system has to continuously adapt its peer list rather than treating disconnection as a failure.

Message propagation: controlled relay, not flood

The naive approach to mesh propagation — every device forwards every message it receives — fails immediately at scale. The network floods, duplicate messages explode, and bandwidth is consumed by traffic that serves no purpose.

DisasterMesh uses a controlled relay approach. Every message carries three pieces of metadata: a unique ID, the sender ID, and a TTL (time-to-live) counter. Each device checks whether it has already seen a message before processing or forwarding it.

Kotlin MeshRepository.kt — deduplication and TTL relay logic 
fun onMessageReceived(message: MeshMessage) {

    // Ignore messages already seen — prevents network flooding
    if (seenMessageIds.contains(message.id)) return

    seenMessageIds.add(message.id)
    processLocally(message)

    // Only relay if the message still has hops remaining
    if (message.ttl > 0) {
        val relayed = message.copy(ttl = message.ttl - 1)
        forwardToAllPeers(relayed)
    }
}

Without deduplication, a single message sent on a 10-device network can generate hundreds of duplicate forwards within seconds. The seen-message ID set is the single most important piece of the propagation logic.

Multi-hop communication: where the system becomes useful

The TTL-controlled relay is what makes multi-hop communication possible. A message from device A does not need a direct connection to device D — it just needs a continuous chain of relay nodes between them. Each relay decrements the TTL by one and forwards. When TTL reaches zero, propagation stops.

This reframes what connectivity means. In a traditional network, connectivity is binary — you either have a path or you do not. In a mesh, connectivity is about reachable paths. A device that cannot see you directly can still receive your message through two or three hops of relay.

Kotlin MeshMessage.kt — message structure 
data class MeshMessage(
    val id:        String,   // unique UUID per message
    val senderId:  String,   // originating device
    val content:   String,   // message payload
    val ttl:       Int,      // hops remaining before propagation stops
    val latitude:  Double?,  // optional location data
    val longitude: Double?,
    val timestamp: Long
)

Location awareness and SOS alerts

DisasterMesh integrates OpenStreetMap for fully offline map rendering. Devices embed their GPS coordinates in outgoing messages, and the map UI plots received alerts in real time. A user can send an SOS with their location attached — that message propagates through the mesh and nearby devices display it on the map.

There are two alert modes: a user SOS that broadcasts a distress signal with location, and an admin broadcast that can set a risk level and radius. The admin mode is designed for first responders or coordinated emergency management.

Because OpenStreetMap tiles can be cached locally on the device, the map continues working even when there is no internet connection. The entire location-awareness layer — map rendering, alert plotting, GPS coordinates — is fully offline.

With background service
Android Service layer
  • Connections maintained in background
  • Message relay continues passively

  • Network stays alive between interactions

MVVM was chosen because mesh state is inherently asynchronous and constantly changing — peers join and leave, messages arrive unpredictably, location updates continuously. With MVVM, the ViewModel holds observable mesh state and the UI reacts to changes without managing lifecycle directly. Without this separation, the UI code becomes unmanageable.

Three reliability challenges that came up in testing

Intermittent connections
Devices disconnect frequently as people move. The system treats disconnection as a normal operating state and continuously rebuilds the peer list rather than treating it as an error.
Duplicate messages
Without the seen-message ID set, the same message appears at every device multiple times within seconds. The dedup filter is the single most load-bearing piece of the propagation logic.
Network fragmentation
The mesh is not always continuous. Some nodes become isolated. The store-and-forward approach means messages can be held and delivered when a connection re-establishes, rather than being dropped.
Dynamic topology
In testing with ~10 devices over ~25 metre range, the network reshaped itself constantly as people moved. This is expected behaviour, not a failure — the system is designed to treat topology as unstable.
“Networking in theory is clean. Networking in reality is chaotic. Real systems must handle partial connectivity, unreliable links, and dynamic topology — and none of that appears in the textbook examples.”

What to improve next

The current propagation model is controlled but still relatively simple — blind relay with TTL. The next meaningful upgrade is smarter routing: building a partial topology map from observed connections so the system can make informed decisions about which peers to forward through, rather than forwarding to all of them.

Priority-based messaging would also make a real difference in an emergency context. Not all messages are equal — an SOS should propagate faster and further than a general message, and the relay logic should reflect that. Better congestion control is the third item, particularly for dense scenarios where many devices are in close range.

Starting fresh: get the deduplication logic right before anything else. It is the difference between a usable network and a flood. Background services are the second priority — without them, the mesh collapses the moment any device locks its screen.
